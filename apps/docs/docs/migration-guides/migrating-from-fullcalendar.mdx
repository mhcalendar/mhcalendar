# Migrating from FullCalendar

FullCalendar is plugin-based (`dayGridPlugin`, `timeGridPlugin`, `interactionPlugin`, ...) and
config-driven through a large flat options object. mhalendar has no plugin system — every view
ships built-in — and the same config-object shape (`viewType` + `events` + callbacks), so most of
the porting work is renaming options and reshaping the event objects.

## Concept mapping

| FullCalendar | mhalendar | Notes |
|---|---|---|
| `initialView: 'dayGridMonth' \| 'timeGridWeek' \| 'timeGridDay' \| 'listWeek'` | `viewType: 'MONTH' \| 'WEEK' \| 'DAY' \| 'AGENDA'` | mhalendar also has `SHIFTPLAN` (resource rows); FullCalendar's `multiMonthYear` has no equivalent. |
| `events: [{ id, title, start, end, allDay }]` | `events: [{ id, title, startDate, endDate, allDay }]` | `start`/`end` → `startDate`/`endDate`. Both are plain JS `Date` objects, not ISO strings. |
| `slotMinTime: '08:00:00'` / `slotMaxTime: '18:00:00'` | `showTimeFrom: 8` / `showTimeTo: 18` | Numbers (0–24), not time strings. See [Display hours](/docs/guides/display-hours). |
| `businessHours: { daysOfWeek: [1,2,3,4,5], startTime: '09:00', endTime: '17:00' }` | `businessHours: [{ dayOfWeek: [1,2,3,4,5], start: 9, end: 17 }]` | Array of entries instead of one object; supports per-date overrides too. See [Business hours](/docs/guides/business-hours). |
| `editable: true` | `allowEventDragging: true` | |
| `eventStartEditable` / `eventDurationEditable` | `allowEventDragging` / `allowEventResize` | mhalendar splits move vs. resize the same way. |
| `eventClick(info)` | `onEventClick(event)` | Receives the mhalendar event object directly, not a FullCalendar `EventApi`. |
| `eventDrop(info)` / `eventResize(info)` | `onEventUpdated(updatedEvent)` | One callback for both move and resize — see [Create & update callbacks](/docs/props/event-lifecycle). |
| `select(info)` + `selectable: true` | `createEventOnClick: true` + `onEventCreated(event)` | mhalendar creates a default-duration event on click rather than a drag-to-select range. |
| `headerToolbar: { left, center, right }` | `showDateSwitcher` / `showViewTypeSwitcher` / `showCalendarNavigation` (booleans) | mhalendar toggles built-in toolbar sections rather than letting you arbitrarily lay out buttons. |

## Before / after

```tsx
// FullCalendar
<FullCalendar
  plugins={[dayGridPlugin, timeGridPlugin, interactionPlugin]}
  initialView="timeGridWeek"
  slotMinTime="08:00:00"
  slotMaxTime="18:00:00"
  editable={true}
  events={events}
  eventClick={(info) => console.log(info.event.id)}
  eventDrop={(info) => persist(info.event)}
/>
```

```tsx
// mhalendar
const config = {
  viewType: 'WEEK',
  showTimeFrom: 8,
  showTimeTo: 18,
  allowEventDragging: true,
  allowEventResize: true,
  onEventClick: (event) => console.log(event.id),
  onEventUpdated: (updated) => persist(updated),
};

<MhCalendar config={config} events={events} />;
```

## Gotchas

- **Event field rename.** `start`/`end` → `startDate`/`endDate` on every event object — this is the
  most mechanical but also most pervasive change; run it as a bulk rename across wherever you build
  event objects.
- **No `revert()`.** FullCalendar's `eventDrop`/`eventResize` let you call `info.revert()` to reject
  a change. mhalendar has no built-in reject path — `onEventUpdated` fires with the already-applied
  change; if you need to reject it, don't write it into your state and re-render with the old data.
- **No plugin imports.** Views, drag/resize, and click-to-create are all built into
  `@mhcalendar/calendar` / `@mhcalendar/react` — there's nothing equivalent to registering
  `interactionPlugin`.
- **Styling isn't CSS-class-based in the same way.** FullCalendar ships CSS files with a large class
  surface to override; mhalendar has no Shadow DOM and is styled through `config.style` (CSS custom
  properties + per-class inline overrides). See [Styling](/docs/styling).
- **No year view.** If you rely on `multiMonthYear`, there's no direct mhalendar equivalent today.
